01 · Outcome

这节课只建立一道门

Week 01 的 AgentLoop 现在依赖可控的 ScriptedModel。下一步不是立即把真实 API 塞进循环，而是先建立一条可以回答“哪些模型配置允许使用”的规则。

看得见的完成标准

在 projects/web-creation-agent-workbench/ 中， Profile loader 能同时读取配置、服务端环境变量和能力检查报告； 任意必要条件不满足时默认拒绝，只向选择器返回 id 和 label。

这是 Week 02 的第一个 Lesson，不是 Week 02 的全部。 本课使用伪造的能力报告验证门禁逻辑；真实 Token、 /responses、流式事件、function calling、错误结构和取消行为 要在后续 Lesson 用真实端点验证。

03 · Basics

配置不是证据

Model Profile 可以理解为一张服务端档案卡。 它告诉应用“去哪里”和“用什么名称”， 但不能证明对方真的理解 Workbench 所需的协议。

信息 它回答什么 它不能证明什么
baseUrl 请求发往哪个 API 根地址。 该地址真的实现了 Responses。
modelId 请求中填写哪个模型标识。 模型支持流式事件或工具调用。
apiKeyEnv 服务端应读哪个环境变量。 密钥一定存在或仍然有效。
CapabilityReport 某次真实检查观察到了哪些能力。 未检查的能力也应默认可用。

五项必要能力

本课先把 Week 02 的验收语言固定成五个稳定的内部名称： 

responses
typed_streaming
function_calling
structured_errors
cancellation

OpenAI 官方文档说明 Responses 流式输出是按 type 区分的语义事件，例如 response.created、 response.output_text.delta、response.completed 和 error。因此，仅能收到分块文本不等于 typed_streaming 已通过。

闭上表格，口头区分

用一句话分别定义 Profile Definition、Capability Report 和 Selector Option。哪一个能离开服务端？

04 · Design

让失败状态默认不可选

  1. 读取 Profile Definition
  2. 校验配置形状
  3. 检查密钥是否存在
  4. 匹配 Capability Report
  5. 输出安全 Selector Option

门禁只有一条通过路径：

definition valid
AND secret exists
AND report exists
AND every required capability passed
→ available

其他所有情况都进入 rejected，并带上可测试的理由。 这叫 fail closed：没有证据时不猜“应该能用”。

两个边界

边界 内部可以知道 外部只能看到
Profile loader Base URL、Model ID、环境变量名、检查报告 是否可用及拒绝原因
Model selector 不需要密钥、Base URL 或检查细节 id 和 label

Step 2 · 实现默认拒绝的 loader

目标：只有配置、密钥和能力证据同时满足时， Profile 才能成为可选项。

继续修改：src/model-profiles.ts

操作提示：先自己写，再展开参考实现。

  1. 为每份 definition 找到同 profileId 的 report。
  2. 检查 id、label、modelId 和 apiKeyEnv 不为空。
  3. 用 new URL() 检查 baseUrl 是 HTTP(S) URL。
  4. 用 env[definition.apiKeyEnv] 检查密钥是否存在。
  5. 用 requiredCapabilities.every(...) 检查全部能力。
  6. 通过时只生成 { id, label }；否则记录拒绝原因。
自己尝试后，展开参考实现 
export type RejectedProfile = {
  id: string;
  reasons: string[];
};

export type LoadResult = {
  available: ModelOption[];
  rejected: RejectedProfile[];
};

function validateDefinition(
  definition: ModelProfileDefinition,
): string[] {
  const reasons: string[] = [];

  for (const [field, value] of Object.entries({
    id: definition.id,
    label: definition.label,
    modelId: definition.modelId,
    apiKeyEnv: definition.apiKeyEnv,
  })) {
    if (!value.trim()) reasons.push(`${field} is empty`);
  }

  try {
    const url = new URL(definition.baseUrl);
    if (url.protocol !== "https:" && url.protocol !== "http:") {
      reasons.push("baseUrl must use HTTP(S)");
    }
  } catch {
    reasons.push("baseUrl is invalid");
  }

  return reasons;
}

export function loadAvailableProfiles(
  definitions: readonly ModelProfileDefinition[],
  reports: readonly CapabilityReport[],
  env: Readonly<Record<string, string | undefined>>,
): LoadResult {
  const available: ModelOption[] = [];
  const rejected: RejectedProfile[] = [];

  for (const definition of definitions) {
    const reasons = validateDefinition(definition);
    const report = reports.find(
      (item) => item.profileId === definition.id,
    );

    if (!env[definition.apiKeyEnv]) {
      reasons.push(`missing env: ${definition.apiKeyEnv}`);
    }

    if (!report) {
      reasons.push("missing capability report");
    } else {
      for (const capability of requiredCapabilities) {
        if (!report.checks[capability]) {
          reasons.push(`missing capability: ${capability}`);
        }
      }
    }

    if (reasons.length > 0) {
      rejected.push({ id: definition.id, reasons });
      continue;
    }

    available.push({
      id: definition.id,
      label: definition.label,
    });
  }

  return { available, rejected };
}

07 · Explain

合上代码，回答五个问题

  1. Model Profile 和具体 API 服务站是什么关系？
  2. 为什么“OpenAI-compatible”不足以让 Profile 可选？
  3. Base URL、Model ID 和 Key 环境变量各自解决什么问题？
  4. 没有 Capability Report 时，loader 为什么必须默认拒绝？
  5. 为什么 Model Option 不包含 Base URL、Model ID 和密钥信息？
先独立回答，再展开核对

1. Profile 是应用内部对一个模型接入方式的规范化描述，具体服务站只是其中一份配置。 2. 兼容声明不能证明 Responses、typed streaming、function calling、错误和取消语义全部符合。 3. Base URL 决定发往哪里，Model ID 决定请求哪个模型，环境变量名让服务端在运行时取得密钥。 4. 缺少证据时允许选择会把未知错当成通过。 5. 选择器只需要安全的公开标识，连接和凭据细节属于服务端。
