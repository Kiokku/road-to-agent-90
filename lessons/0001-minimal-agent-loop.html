Lesson 0001 · Week 01 · Agent Runtime

让工具结果
回到模型

你将为 Web Creation Agent Workbench 写出第一条真正的因果链： 模型请求读取项目 Brief，应用执行只读工具，把结果精确回填给同一次调用， 模型再给出最终回答。

Timebox
90 分钟实现 + 15 分钟讲解
Deliverable
TypeScript CLI + 4 条 Vitest 路径
Boundary
无真实 API、无 UI、无文件写入

本课路线

  1. 定义成果
  2. 建立心智模型

01 · Outcome

先定义“完成”

这一课不追求“连上一个模型”。你要证明的是：即使模型由确定性的测试替身提供， Workbench 也能正确拥有循环、工具执行、结果关联与停止权。 这正好填补 Learning Record 0003 记录的能力空白。

本课唯一纵切

输入“读取 demo-landing-page 的项目 Brief 并总结”，模型端口先返回 read_project_brief 调用；应用执行工具并回填结果；模型端口随后返回最终摘要。

  • npm test 通过四条关键路径。
  • npm run demo 打印完整的 request → tool → output → final 链路。
  • 你能不看代码解释 call_id 和最大轮次为何不可省略。

02 · Knowledge

Agent Loop 不是“模型自己执行工具”

官方 Function Calling 指南把工具调用描述为模型与应用之间的多步协作： 模型只产生结构化调用，真正的代码由应用执行，工具结果再进入下一次模型请求。 一次模型响应也可能继续请求更多工具，因此停止条件属于应用，而不属于模型。

  1. 携带工具发起请求
  2. 收到函数调用
  3. 应用执行代码
  4. 回填工具结果
  5. 收到最终回答

Responses API 使用带类型的 Item。工具请求是 function_call，工具结果是 function_call_output；后者必须用 call_id 指向它正在回答的那一次调用。

一手资料： 阅读 OpenAI 的 The tool calling flow； 需要核对 Item 映射时再看 Map Messages to Items。 先只读这两个小节，不扩展到 streaming。

03 · Design

先固定边界，再写循环

不要让核心循环直接依赖真实 SDK。定义一个很窄的 ModelPort，测试时注入脚本化模型；下一课接入 Profile 时， 只需实现新的 adapter，不必重写 orchestration。 

type InputItem =
  | { type: "user"; content: string }
  | FunctionCall
  | { type: "function_call_output"; callId: string; output: string };

type FunctionCall = {
  type: "function_call";
  callId: string;
  name: "read_project_brief";
  arguments: string;
};

type OutputItem =
  | FunctionCall
  | { type: "message"; text: string };

interface ModelPort {
  respond(input: InputItem[]): Promise<{ output: OutputItem[] }>;
}

这里故意使用项目自己的最小类型，而不是复制完整 OpenAI SDK 类型。 但保留 function_call、function_call_output 和 callId 这些协议语义，避免测试一个与真实 API 无关的假循环。

工具契约

唯一工具 read_project_brief 接受 {"briefId":"demo-landing-page"}。它只读取代码内的固定 fixture， 返回版本、目标受众与页面目标；不访问网络、不写文件。

参数失败也是 observation

JSON 无法解析或 briefId 不合法时，不让整个进程崩溃。 生成结构化失败的 function_call_output 回给模型， 让下一次响应有机会解释或纠正；达到最大轮次时则由应用强制停止。

04 · Practice

在主作品里完成它

所有实现都放在 projects/web-creation-agent-workbench/。 使用最小 npm + TypeScript + Vitest 配置，不创建 React 应用，也不安装 OpenAI SDK。

  • src/agent-loop.ts循环、终止条件与公开类型
  • src/read-project-brief.ts参数解析和只读工具
  • src/scripted-model.ts确定性的 ModelPort 测试替身
  • src/demo.ts打印一次完整运行
  • test/agent-loop.test.ts四条行为测试
  1. 初始化 TypeScript 项目，让 npm test 运行 Vitest， 让 npm run demo 通过 tsx 执行 CLI。
  2. 先写“模型直接回答”的测试与最小实现。此时循环只能调用模型一次并返回 message。
  3. 再写“模型调用工具”的测试。第二次传给模型的 input 必须同时包含原输入、 原 function_call 和匹配 callId 的输出。
  4. 增加参数失败路径。断言工具没有被错误执行，同时失败 observation 被回填。
  5. 最后加入 maxTurns。让脚本化模型永远请求工具， 断言循环以明确错误停止，而不是挂起。

实现约束

一个 for 循环、一个工具分派点、一个最大轮次检查就够了。 不要提前创建通用工具注册框架、事件总线、Session、SSE、React UI 或真实 provider。

05 · Feedback loop

让失败路径证明设计

测试行为，不测试私有函数。脚本化模型应记录每次收到的 input， 这样测试能直接观察工具结果是否被正确关联并回填。

路径 安排 关键断言
工具成功 call → final 执行一次；输出沿用原 callId；最终文字返回
参数失败 bad call → final 不崩溃；回填结构化 error observation
无需工具 final 只请求模型一次；工具执行次数为零
超过轮次 call → call → … 在 maxTurns 后抛出可识别的限制错误 
cd projects/web-creation-agent-workbench
npm test
npm run demo

演示输出不必逐字相同，但必须让旁观者看见因果顺序：

[request] 读取 demo-landing-page 的项目 Brief 并总结
[function_call] read_project_brief · call_001
[function_call_output] call_001 · {"version":"v1", ...}
[final] 已读取 v1 Brief：为……创建响应式单页。

如果 demo 只能显示最终回答，纵切还不算“可演示”； 如果 demo 能跑但四条测试未通过，也还不能写入 Evidence。

06 · Retrieval

合上代码，讲清因果链

5 分钟闭卷挑战

  1. 画出五步工具调用流程，并标出哪两步属于应用。
  2. 解释为什么工具 output 必须带原调用的 call_id。
  3. 解释模型不断请求工具时，为什么应用必须拥有停止权。
  4. 回答：Agent 与一次普通 LLM 请求的本质区别是什么？
完成闭卷回答后，再展开核对

核心不是“多请求一次”，而是应用维护一个受控循环： 它把模型提出的动作映射到真实工具，执行并观察结果，再把观察与对应调用关联后继续推理； 同时由应用验证参数、限制权限并决定何时终止。

完成后的证据

保存测试终端输出与 demo transcript，但现在不要新建 Learning Record。 只有你完成实现、四条测试通过并能闭卷解释后，才让教师核验并记录成果。 本课完成前，不进入 Model Profile、真实 Token 或 streaming。

卡住时就问教师

把失败测试、你预期的 input items 和实际收到的 items 一起发给 Agent。 优先问“哪一段因果链不成立”，不要直接索取整份答案。
